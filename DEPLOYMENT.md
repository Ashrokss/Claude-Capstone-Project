# Deploying VeriClaim

Frontend on Netlify, backend on Render, database and auth already on Supabase.

## Why the split

The frontend is an ordinary Next.js app and deploys to Netlify unchanged. The
backend cannot go there, and the reason is structural rather than a
configuration gap:

**The analysis worker is long-lived.** `job_queue.py` starts an asyncio worker
pool at application startup that runs for the life of the process. A serverless
function has no life beyond its response — the queued task is killed the moment
the handler returns.

**Analysis takes minutes, not seconds.** Measured runs took roughly 100 and 170
seconds; the job ceiling is 900s, raised after an observed 304s run. Netlify's
synchronous functions cap at 10s, and its background functions are
JavaScript-only. Vercel does run Python, but caps at 60s on Hobby and 300s on
Pro, and would still kill the worker pool.

So the backend runs as a container. `backend/Dockerfile` already exists, so
Render needs no new build tooling.

---

## Order matters

The frontend needs the backend's URL at **build** time, and the backend needs
the frontend's origin for CORS. Deploy the backend first, then the frontend,
then set the one value that closes the loop.

---

## 1. Apply migrations

The schema lives in Supabase, which is reachable from anywhere, so this runs
from your machine against the same database the deployed backend will use:

```bash
docker compose run --rm migrate
```

Deploying never mutates the database as a side effect. That is deliberate —
keep it a separate, considered step.

## 2. Deploy the backend to Render

1. Render dashboard → **New** → **Blueprint** → select this repository.
   `render.yaml` is picked up automatically.
2. Render will prompt for every variable marked `sync: false`. Copy them from
   `backend/.env`:

   | Variable | Source |
   | --- | --- |
   | `DATABASE_URL` | Supabase → Connect → **Session pooler** (not the direct connection — on the free tier that endpoint is IPv6-only and will time out) |
   | `SUPABASE_URL`, `SUPABASE_KEY` | Settings → General, Settings → API Keys |
   | `SUPABASE_SERVICE_ROLE_KEY` | Settings → API Keys → Secret keys |
   | `SUPABASE_JWT_SECRET`, `SUPABASE_JWT_AUDIENCE` | Settings → JWT Keys |
   | `NVIDIA_API_KEY`, `NVIDIA_BASE_URL`, `NVIDIA_MODEL` | your `backend/.env` |
   | `GEMINI_API_KEY`, `GEMINI_MODEL` | your `backend/.env` |
   | `FRONTEND_URL` | leave as a placeholder for now; step 4 fixes it |

3. Deploy, then confirm `https://<service>.onrender.com/health` returns 200.

`SECRET_KEY` is generated by Render. Do not paste the development one.

## 3. Deploy the frontend to Netlify

1. Netlify → **Add new site** → **Import from Git** → this repository.
   `netlify.toml` sets the base directory, build command and Node version.
2. Site configuration → **Environment variables**, add three:

   ```
   NEXT_PUBLIC_SUPABASE_URL       https://<project>.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY  <publishable key — public by design>
   NEXT_PUBLIC_API_URL            https://<service>.onrender.com
   ```

3. Deploy.

`NEXT_PUBLIC_*` values are compiled into the client bundle at build time.
Changing one later needs a **fresh deploy**, not a restart — a restart leaves
the browser running whatever was compiled in. This is the single most common
way to lose an afternoon here.

## 4. Close the CORS loop

Back in Render, set `FRONTEND_URL` to the Netlify origin exactly — scheme, no
trailing slash:

```
FRONTEND_URL=https://<your-site>.netlify.app
```

Save and let it redeploy. Until this is right, every authenticated request is
blocked by the browser and the UI reports that it cannot reach the claims
service.

## 5. Close registration — both halves

`netlify.toml` sets `NEXT_PUBLIC_ALLOW_SIGNUP=false`, which hides the sign-up
control and refuses the call in the client.

**That is not the boundary.** Supabase's auth API is reachable by anyone holding
the publishable key, which by design ships in the browser bundle. Anyone who
opens devtools can still register. So also:

**Supabase → Authentication → Sign In / Providers → disable email signups.**

Then create the demo accounts by hand under Authentication → Users, with
confirmed addresses so no inbox is needed, and grant adjuster access by setting
`app_metadata`:

```json
{ "role": "claims_employee" }
```

Use real-looking addresses rather than the `.test` ones from local development.
`.test` is a reserved TLD, and while the read-path bug it exposed is fixed,
there is no reason to keep tripping over it.

Why this matters: every claim submitted spends real NVIDIA and Gemini quota. An
open sign-up form on a public URL is an open tab against your account.

## What to expect from the free tiers

**Render free instances sleep after about 15 minutes idle.** The first request
afterwards pays a cold start of roughly 30–60 seconds, and because the analysis
queue is in-process, anything queued when it slept is gone. The claim is not
lost — **Re-run analysis** in the adjuster console recovers it.

If you are demonstrating live, hit the URL a few minutes beforehand so the
instance is warm. Or upgrade to a paid instance, which removes both the sleep
and the lost-queue problem.

**Analysis still takes one to five minutes.** That is provider latency, not
hosting. It does not improve on a bigger instance.

## Known issues that affect a deployed demo

Both are in `KNOWN_ISSUES.md` in the submission package, and both bite harder in
a hosted environment than locally.

**Evidence uploads race the first analysis.** `POST /claims` queues analysis
before the browser has finished uploading, so a freshly submitted claim can be
assessed with no photograph or policy attached. A slower network makes this
*more* likely, not less. Use **Re-run analysis**, and for a live demo prefer a
claim that is already assessed — submit a fresh one only to show the intake
journey.

**The vision provider goes down sometimes.** Gemini returned 503 three times
during screenshot capture. The orchestrator retries, then degrades that step and
completes the assessment with the gap labelled. Worth knowing before you present
an assessment with no damage items and have to explain it on the spot.

## If you would rather not split the deployment

Render can host both services from the same blueprint — add the frontend as a
second `type: web` service using `frontend/Dockerfile`, and skip Netlify
entirely. One dashboard, one set of logs, and the `NEXT_PUBLIC_*` values move to
Docker build arguments.

The trade is that Netlify's CDN and preview deploys are better than Render's for
a frontend. For a showcase demo either is fine.
